## How this project works (read before doing anything)

This project is built entirely through the **`superpowers`** Claude Code plugin's skill pipeline. Every phase follows the same sequence:

1. **`superpowers:brainstorming`** — classify the work as spike/bounded/architectural, ask clarifying questions one at a time, propose approaches, present a design section-by-section, get explicit approval. For architectural work, this ends with a written spec at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed to git.
2. **`superpowers:writing-plans`** — turns the approved spec into a granular, TDD-structured implementation plan at `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` — bite-sized tasks, each with exact code, exact test assertions, no placeholders.
3. **`superpowers:subagent-driven-development`** — executes the plan: a fresh subagent per task, an independent task reviewer after each one (spec compliance + code quality), a ledger at `.superpowers/sdd/<plan-basename>/progress.md` tracking everything, a capped fix-loop when reviewers find real issues, and a final whole-branch review (on the most capable model) before merge.
4. **`superpowers:finishing-a-development-branch`** — merge/cleanup (the user has been doing actual merges themselves via GitHub PRs).

**Non-negotiable standing rules, all in `CLAUDE.md`:**
- **Explain-as-you-go**: before any implementation step, explain what/why/how; after, explain what changed and what it means. One piece at a time, confirmed before moving on. No silent scope growth.
- **Phased development**: each phase ends with real testing (pytest against real data, no mocks of `portfolio.db`) before the next phase is even planned. Once a phase's tests pass and it's merged, push `main` before starting the next phase's brainstorming.
- **Agentic workflow design principles** (11 of them): workflows before agents, small single-purpose units, explicit typed state (`TypedDict`s in `state.py`), separate gather/measure from judge/decide, fail loud never fabricate, tools as external MCP protocols not ad-hoc logic, guardrails as structure not instruction, reject-early gating, human-in-the-loop at consequential decisions, memory as a deliberate choice, observability is not optional.
- **LLM cost control** (7 rules): explicit per-node model choice (never silent default), reject-early before expensive calls, cacheable stable system prompts, minimal context per call, hard numeric caps enforced in code, bounded retries, long-term memory as a cost control.
- **Non-negotiable guardrails**: advisory only, never execution (no order-placement tool anywhere, ever); long-term investing only (no options/derivatives/day-trading); `portfolio.db` is read-only always (`mode=ro` URI, never edit `portfolio_data_mcp/server.py`); agent writes go only to `sandbox-data/agent_memory.db`; new-buy candidates must clear the full Conviction Gate or be explicitly rejected — "avoid is the default, not buy."

**Verification habit used throughout this session, worth continuing:** never trust a library's documented API shape — verify it live (`python -c "..."` against the actually-installed version) before writing plan code. This caught several real surprises (MCP tool result shapes, `yfinance-mcp`'s `symbol` not `ticker` argument, a webpage-only model alias that wasn't a valid API ID, `FilteredToolset` not exposing `direct_call_tool`). Reviewers in this session also independently re-verified claims rather than trusting reports — re-running tests themselves, reading library source to confirm a monkeypatch pattern, hand-tracing cap logic against concrete scenarios. Keep that standard.

## What's actually done (merged to `main`, tested, working)

**Phase 1 — Research node.** `src/agentic_frameworks/graph/nodes/research.py`. Fetches real holdings via the existing `portfolio_data_mcp` server (a separate project at `E:\agentic-portfolio-dashboard`, its own venv, launched as a stdio subprocess). Groups holdings by asset_class × geography. Real portfolio: ₹10.29M, mixed IN/US, mixed equity/fund/real-estate.

**Phase 2 — Risk Analyst node.** `src/agentic_frameworks/graph/nodes/risk_analyst.py`. Pure functions (no LLM, no MCP) computing four risk views from Research's output: concentration, category overlap (sector-based diversification proxy), currency exposure, liquidity (real-estate vs everything else). Reports raw numbers only, no verdicts — judgment is deferred to later nodes.

**Phase 3 — Graph Harness.** `src/agentic_frameworks/graph/graph.py`, `checkpointer.py`. First time the system ran as an actual `StateGraph`, not isolated functions. Linear `Research → Risk Analyst`, backed by a real `AsyncSqliteSaver` checkpointer writing to `sandbox-data/agent_memory.db` (gitignored, created fresh). Proved memory persistence works via a real end-to-end run.

**Phase 4 — US Equity/ETF Specialist.** `src/agentic_frameworks/graph/nodes/us_equity_etf_specialist.py`. First LLM-calling node, first `pydantic-ai` usage, first real spend of money on a paid API. Three-stage pipeline: (1) an LLM candidate generator proposes tickers per gap sector, capped in code at 3/sector and 5/run (never trusting the model's own count); (2) each candidate is verified against real `yfinance-mcp` data before any expensive evaluation runs (reject-early — this is also the safeguard against LLM-hallucinated tickers, since a fake ticker returns a near-empty payload rather than raising, and `longName` presence is the confirmed reliable signal); (3) surviving candidates go through a Conviction Gate evaluator (portfolio-fit → fundamentals → valuation → style-fit, reject-early on first failure), producing a strictly validated `CandidateEvaluation` per candidate.

- **Model:** `deepseek/deepseek-v4.1-flash` primary via OpenRouter, `z-ai/glm-5.3-flash` backup (added mid-phase after DeepSeek's shared free pool returned genuine repeated 429s — confirmed via `pydantic_ai.models.fallback.FallbackModel`, which triggers on `ModelAPIError`, live-confirmed a 429 raises as a subclass of that).
- **Data source:** `yfinance-mcp` (external package, launched via `uvx yfmcp@latest`, not a project dependency — same "sibling subprocess" pattern as `portfolio_data_mcp`). Covers US equity, US ETF fundamentals/holdings, AND India equity (via `.NS` ticker suffix, live-verified against real NSE stocks). Options/derivatives/intraday-gapper tools are structurally excluded from the toolset via `.filtered()` — not just told not to use them, actually can't reach them.
- **Required real-model gate:** every LLM-calling phase must include one real, deliberate, cost-bounded run against the actual paid model, reviewed by the user, before the phase counts as done — this is what caught a genuine bug (`confidence` field had no bounds, model returned `7.0` once) that no amount of `TestModel`-only testing could have found. `TestModel` (free, `pydantic_ai.models.test`) is used for all automated tests of LLM-calling logic; the real check is separate and manual.
- **Post-merge fix (2026-09-11, bounded, no branch):** the portfolio-fit check was a tautology (told a sector is a gap, asked to confirm it, no real data). Fixed: the node now builds a real holdings summary from `state["holdings_by_bucket"]` at call time (not hardcoded), baked into the Conviction Gate's system prompt. Verified end-to-end against the real graph output — genuinely reflects your actual 6 US holdings (GOOGL, IBM, MU, SMH, VOO, IAU), and updates automatically as the portfolio changes.

**Phase 5 — India Equity Specialist.** `src/agentic_frameworks/graph/nodes/india_equity_specialist.py`. Second new-buy specialist, same three-stage pipeline as Phase 4 (propose → verify → Conviction Gate), reusing the same model pair and `yfinance-mcp` toolset (already confirmed to resolve `.NS`-suffixed NSE tickers). One real design change from Phase 4: gap sectors are **computed live from real holdings** (`_compute_india_equity_gaps`, `_compute_us_gaps`), not a hardcoded list — this also retrofitted a real bug fix into the Phase 4 US specialist, whose hardcoded `US_GAP_SECTORS` list was found to omit "Information Technology" (frozen at a point in time when the portfolio already held it). `ProposedCandidate.sector` was generalized to validate against the full 11-bucket GICS taxonomy (`GICS_SECTORS`), shared by both specialists. Both specialists are now wired into `build_graph()` as parallel branches off `risk_analyst` — the graph's first real fan-out (both still dead-end at `END`, no Synthesizer yet). `_apply_candidate_cap` was extracted into a shared `nodes/_specialist_helpers.py` module to avoid duplicating cap logic between specialists.

- **Design decisions, confirmed with the user during this phase's brainstorming:**
  - Gap computation is equity-only for both specialists — ETF `sector` values (e.g. "US Large Cap", "Gold") aren't real GICS sectors, and mutual fund `sector` values are fund *category* not GICS sector; including either would mean fabricating coverage that isn't actually known. Whole-portfolio gap analysis (rolling up sector coverage across mutual funds too) was explicitly deferred to the future Mutual Fund Specialist phase, which can supply real fund-holdings sector data.
  - **Real estate is the one exception:** since the user's real estate holding is a directly known fact (not an inferred category), `_compute_india_equity_gaps` treats "Real Estate" as covered whenever `holdings_by_bucket["real_estate"]["IN"]` is non-empty — confirmed against the real portfolio to correctly leave `{"Energy"}` as the only current India equity gap (previously `{"Energy", "Real Estate"}` before this fix).
- **Post-final-review fixes (same phase, before merge):**
  - The whole-branch review caught that widening `ProposedCandidate.sector` to the full GICS taxonomy (needed for live gap computation) removed the schema-level guarantee that a candidate actually addresses a gap. Fixed: a shared `_filter_to_gap_sectors` helper drops off-gap candidates before the cap/verification/evaluation stages, in both specialists. Also added reject-early: both nodes now return an empty candidate list immediately if the live gap list is empty, before any model/toolset setup — avoiding a real LLM call on an empty-content prompt.
  - **Real-model verification (2026-09-11) caught a second, more serious bug:** `get_yfinance_toolset()` had `tool_error_behavior="error"`, meaning ANY tool-call problem (including a benign one, like the model omitting a required argument) crashed the whole node with a hard `fastmcp.exceptions.ToolError`, rather than giving the model a bounded chance to self-correct via `ModelRetry` (already bounded by the existing `Agent(retries=2)`). This crashed the very first real-model run, live, on a real `yfinance_get_price_history` call missing its `symbol` argument. Fixed by switching to the library default `tool_error_behavior="retry"`. Re-verified: a subsequent real run hit two more real, legitimate tool errors (yfinance 404s for ONGC.NS and XLF fundamentals data) and recovered gracefully instead of crashing, producing 5 real US candidates (Health Care: XLV/UNH/JNJ Hold/Buy/Hold; Financials: XLF/JPM Buy/Hold) and 3 real India candidates (all Energy: RELIANCE.NS/ONGC.NS/IOC.NS, all Buy) — reviewed by the user, all confidence values valid (0.6–0.72), all genuinely advisory, no fabricated data.

**Phase 6 — Mutual Fund Specialist.** Two new, single-purpose nodes covering the real 9 IN mutual fund holdings: `mutual_fund_holdings_analyzer_node` (`src/agentic_frameworks/graph/nodes/mutual_fund_holdings_analyzer.py`, judges existing holdings — first node in this project to do real LLM-driven judgment of *existing* holdings, not just new-buy candidates) and `mutual_fund_specialist_node` (`.../mutual_fund_specialist.py`, proposes/evaluates new-buy candidates, mirroring the equity specialists' propose→verify→evaluate pipeline). Both wired into `build_graph()` as two more parallel branches off `risk_analyst` — the graph now has 4 parallel branches, all still dead-ending at `END`.

- **First custom, self-written MCP server this project has built:** `src/agentic_frameworks/mfapi_mcp/server.py`, wrapping `MFapi.in` (free, no-auth Indian mutual fund NAV/scheme API) with `search_scheme`, `get_scheme_nav`, and `get_scheme_meta` (a lightweight `/latest`-endpoint tool added during final review to avoid downloading full NAV history just to check a scheme's ISIN/category). Built with the official MCP SDK's `mcp.server.fastmcp.FastMCP` (already installed transitively via `pydantic-ai`, no new dependency). Chosen over several pre-built MFapi-wrapping MCP servers found on the market, after determining none of them covered this project's actual requirements (ISIN-matched resolution against exact holdings, category-gap detection against a curated taxonomy, cross-fund redundancy across the specific 9 real funds) — those are business logic no generic tool would have. This also picks up the "build an MCP server yourself" learning goal explicitly deferred from Phase 4's `yfinance-mcp` reuse decision.
- **A substantial new pure-computation layer** (`src/agentic_frameworks/graph/nodes/_mutual_fund_helpers.py`), mirroring the Risk Analyst's measure-not-judge pattern: ISIN-matched scheme-code resolution (deterministic, with progressive-query-shortening and letter-digit-normalization fallbacks, live-verified against all 9 real holdings including one genuine naming-mismatch edge case — "Nifty200" vs `MFapi.in`'s "Nifty 200"), NAV-history fetching/parsing, CAGR/volatility/max-drawdown metrics (stdlib `statistics` only, no numpy/pandas — confirmed not even installed in this project's venv), benchmark-difference computation via the already-integrated `yfinance-mcp` (a curated `MF_CATEGORY_BENCHMARK_TICKERS`/`INDEX_FUND_BENCHMARK_TICKERS_BY_ISIN`, live-verified: exact-index matches for 2 of 4 existing index funds, category-proxy matches for equity categories, confirmed unavailable for hybrid/debt categories), and cross-fund NAV-return correlation (a statistical proxy for portfolio-holdings overlap, which no free data source exposes directly).
- **A redefined 7-check Conviction Gate for funds** (portfolio-fit/redundancy → cost (qualitative Direct-vs-Regular only, since `MFapi.in`/AMFI's own feed confirmed to have no expense-ratio field at all) → performance-vs-benchmark → risk-adjusted performance (volatility + max drawdown, not Sharpe — no clean Indian risk-free-rate source found) → cross-fund redundancy → track-record length → style-fit), with static India MF tax-treatment domain knowledge (equity vs. debt fund capital-gains rules, ELSS's 3-year lock-in) baked into both nodes' system prompts.
- `MF_CATEGORY_TAXONOMY` (13 curated categories) was deliberately placed in `schemas.py` alongside `GICS_SECTORS`, matching this project's established layering (node modules import taxonomy constants from `schemas.py`, never the reverse) — caught and fixed during this phase's own pre-flight review before any code was written.
- `_apply_candidate_cap`/`_filter_to_gap_sectors` (shared by all three new-buy specialists) were generalized to accept a `key=` parameter (default `lambda c: c.sector`, unchanged for the two equity specialists; `lambda c: c.category` for mutual funds) — zero behavior change to existing callers.
- **Explicitly out of scope, disclosed:** category peer-ranking (comparing a fund against all peers in its category, not just one benchmark index — a real, larger cost/scope expansion, deferred); true Sharpe/Sortino ratios; client risk-profile/goals-based asset-allocation suitability (no such data exists anywhere in this system); AMC/fund-manager governance/news monitoring (a web-search-shaped capability, same tradeoff already rejected in this project); numeric expense ratio and AUM (confirmed unavailable from every free source checked); underlying portfolio-holdings concentration within a fund.

**Phase 7 — LangGraph Store (cross-run rejection memory).** `src/agentic_frameworks/graph/store.py` (new), `src/agentic_frameworks/graph/nodes/_candidate_memory.py` (new), `schemas.py` (`RejectedCandidate` added), and the three new-buy specialist nodes (`us_equity_etf_specialist.py`, `india_equity_specialist.py`, `mutual_fund_specialist.py`, all modified). Gives the graph its first real long-term/cross-run memory, and uses it as a cost control: a candidate that already failed the Conviction Gate in a prior run is no longer re-verified/re-evaluated (a paid LLM call) on the next run without new information. Design spec: `docs/superpowers/specs/2026-09-18-langgraph-store-design.md`.

- **Store choice:** `AsyncSqliteStore` (`langgraph.store.sqlite.aio`), pointed at the same `sandbox-data/agent_memory.db` the checkpointer already writes to (`AGENT_MEMORY_DB_PATH` imported from `checkpointer.py`, never re-derived) — `get_memory_store()` mirrors `get_checkpointer()` exactly. Live-verified this phase: checkpointer and store share the one WAL-mode file cleanly across the graph's real four-parallel-branch fan-out, writing to disjoint tables (`checkpoints`/`writes` vs. `store`/`store_migrations`) — confirmed via a dedicated coexistence test (`test_graph.py::test_graph_coexists_checkpointer_and_store_on_same_file_under_real_fan_out`).
- **"Rejected" means a non-Buy Conviction Gate verdict on a new-buy candidate.** Buy is never suppressed — a live buy recommendation is the product and must stay fresh every run. `RejectedCandidate` (`schemas.py`) reuses `CandidateEvaluation`'s own `identifier`/`identifier_kind`/`display_name` identity convention (upper-cased ticker for equity/ETF, scheme_code string for mutual funds, plus one addition — `"scheme_name"` — for the mutual fund alias-index record only) rather than inventing a separate identity scheme, per a mid-phase correction requested after a concurrent, unrelated bugfix landed the same identity convention on `CandidateEvaluation`.
- **Filter order in each specialist:** live gap filter → rejection filter (`_filter_previously_rejected`, keyed off the same identity used to write records) → `_apply_candidate_cap` (unchanged, 3/group-5/run) → verification → paid evaluation. Suppressed candidates consume no cap slot, so a run that only sees old rejects still evaluates fresh ideas where they exist — pinned by a dedicated cap-interaction test.
- **Mutual funds get a two-stage filter** (design spec's asymmetry: equity tickers are pre-verified by generation time, funds are not): a cheap pre-cap filter on the normalized proposed name (`_normalize_scheme_name` — case-fold, strip punctuation, drop noise words fund/direct/plan/growth/scheme), then the authoritative filter on the real, MFapi-resolved `scheme_code`, run immediately before the paid evaluator call. Both alias and canonical records are written on a non-Buy verdict. A dedicated test (`test_mutual_fund_specialist_node_catches_renamed_proposal_via_scheme_code_stage`) proves a renamed proposal that misses the cheap alias filter is still caught by the authoritative one, using two real MFapi.in-resolvable name variants of the same real fund (scheme_code 120605).
- **Staleness enforced in code, not via store TTL:** a rejection suppresses re-evaluation only while `rejected_at` is within `REJECTION_MEMORY_DAYS = 90` (a module constant). A TTL is still written on every record as belt-and-braces garbage collection, but nothing correctness-relevant depends on it — the installed `langgraph-checkpoint-sqlite` version has a live-verified MRO quirk (`BaseStore.supports_ttl = False` shadowing the sync store's `True`) that means `AsyncSqliteStore` does not actually omit expired items from reads.
- **Generator exclusion hints:** each specialist's candidate-generator prompt gets up to `MAX_EXCLUSION_HINTS = 20` recently-rejected display names appended as a "do not propose these" hint, to reduce wasted evaluator calls — a prompt-level optimization only; the in-code rejection filter stays authoritative regardless of whether the model honors the hint.
- **Fund ISIN→scheme_code resolution caching** (`resolved_schemes/mutual_fund` namespace) — accepted in scope per the design spec's Decision 3. **Deviation from the spec as written:** the spec's own reasoning ties this to `_resolve_scheme_code` (the ISIN-based, progressive-query-shortening resolver used only by `mutual_fund_holdings_analyzer_node`), but the same spec and this phase's explicit task instructions both say that node gets **no** store integration and stays untouched. Since a not-yet-held new-buy candidate has no ISIN to key on anyway, the cache was instead wired into `mutual_fund_specialist_node`'s own resolution step (`_resolve_scheme_by_name_and_direct_plan`), keyed by normalized proposed name rather than ISIN — same "don't repeat expensive-ish free-API work every run" cost-control spirit, applied to the one node actually in scope for modification this phase. No TTL on this cache: a fund's real identity doesn't change once resolved.
- **Fail-loud store guard:** every store-using node opens with an explicit `if store is None: raise ValueError(...)` — LangGraph injects `None` (not an exception) when a graph is compiled without a store, so without this guard a call site that forgot `store=` would silently disable the whole cost control forever. Verified live this phase and worth flagging for future signature-injected kwargs on this LangGraph version: injection is a literal *string* match against the function's stored `__annotations__` (this project uses `from __future__ import annotations` everywhere, so annotations are unevaluated source strings) — `store: BaseStore | None = None` does **not** match LangGraph's accepted `"Optional[BaseStore]"` string and silently fails to inject (no error, `store` just arrives as `None` even when the graph *was* compiled with `store=...`). Fixed by writing the signature as `store: Optional[BaseStore] = None` (importing `typing.Optional`), the exact source text LangGraph's injector checks for.
- `graph.py` itself is unchanged (as the spec specifies) — it still returns an uncompiled `StateGraph`; call sites (`test_graph.py`, and the future real-run entry point) compile with both `checkpointer=` and `store=`.
- **29 new tests, all passing** (127 total tests collected at the end of this phase's fix round, vs. 98 at the prior commit `HEAD` — corrected from an earlier undercount of "13"; 27 of the 29 were added during the original Phase 7 build, 2 more — India parity for the US specialist's cross-run-suppression/never-suppresses-Buy tests — added during the post-review fix round below): store wiring (`test_store.py`), the shared helpers (`test_candidate_memory.py` — normalization, freshness boundary, load/filter/record round-trip, cap interaction, resolved-scheme cache round-trip), plus per-specialist additions (fail-loud-without-store, cross-run suppression counted via a deterministic fake evaluator — TestModel alone can't exercise this path since it deterministically emits `action="Buy"`, the one verdict this design never suppresses — Buy-never-suppressed, and the mutual fund two-stage catch). `portfolio.db` mtime confirmed identical before and after the full suite.
- **Real-model verification (manual, not automated, per this phase's scope):** deliberately not run as part of this build — bounded per CLAUDE.md's LLM cost control rules and the project's "skip real paid calls unless explicitly asked" convention for automated work. To run it manually: compile the real graph with both `get_checkpointer()` and `get_memory_store()` (no `TestModel` monkeypatching) and `ainvoke` it twice against the real `portfolio.db`, confirming visually that the second run's specialist candidate lists omit whatever the first run rejected. Concretely:
  ```python
  import asyncio
  from agentic_frameworks.graph.checkpointer import get_checkpointer
  from agentic_frameworks.graph.store import get_memory_store
  from agentic_frameworks.graph.graph import build_graph

  async def main():
      async with get_checkpointer() as checkpointer, get_memory_store() as store:
          compiled = build_graph().compile(checkpointer=checkpointer, store=store)
          for i in range(2):
              result = await compiled.ainvoke({}, config={"configurable": {"thread_id": "real-verification-run"}})
              print(f"--- run {i + 1} ---")
              print("US:", [(c["identifier"], c["action"]) for c in result["us_equity_etf_candidates"]])
              print("India:", [(c["identifier"], c["action"]) for c in result["india_equity_candidates"]])
              print("MF:", [(c["identifier"], c["action"]) for c in result["mutual_fund_candidates"]])

  asyncio.run(main())
  ```

**Phase 8 — Recommendation Synthesizer + full graph fan-in + human-approval gate.** `src/agentic_frameworks/graph/nodes/synthesizer.py` (new), `src/agentic_frameworks/graph/nodes/human_approval_gate.py` (new), `schemas.py` (`SynthesizedHoldingGuidance`/`SynthesizedNewBuy`/`SynthesizedRecommendation`, `ExistingHoldingGuidance`/`NewBuySuggestion`/`ReportCoverage`/`AdvisorReport`, `HumanApproval` all added), `state.py` (`SynthesizerState`/`ApprovalState` added, `GraphState` gains `recommendation`/`approval`), `models.py` (`get_synthesizer_model()` added), `graph.py` (all four `-> END` edges now route to `synthesizer`; new conditional edge to `human_approval_gate` or `END`; new additive `build_compiled_graph(*, checkpointer, store)` factory). > **NEEDS ABHI'S SIGN-OFF — not yet reviewed, do not trust for real money yet:** `MAX_NEW_POSITION_PCT = 2.0` and `MAX_NEW_CAPITAL_PCT = 5.0` (`schemas.py`) are real-money position-sizing bounds — 2% of the real ₹10.29M portfolio is roughly ₹2 lakh per suggestion — accepted as a conservative, industry-common **default** during an autonomous overnight session, not a final decision. The *structural* guardrail (a hard numeric ceiling enforced in code — schema `Field(le=MAX_NEW_POSITION_PCT)` per suggestion, plus a code-level aggregate check in the Synthesizer's `output_validator` — never soft LLM prompt wording) is non-negotiable and already fully in effect; what's unreviewed is only whether *these specific percentages* are the right ones. This doesn't change the advisory-only guardrail (nothing here ever executes a trade either way), but no new-buy suggestion sized against these constants should be treated as vetted until Abhi has explicitly reviewed the two numbers. Both are named constants in `schemas.py`, trivial to change in one place.

- **Two-layer identity split, extended from Phase 7's pattern.** `SynthesizedRecommendation` (the LLM's `output_type`) carries `identifier` only on both `SynthesizedHoldingGuidance` and `SynthesizedNewBuy` — no `display_name`/`identifier_kind`/`specialist` anywhere in that schema tree (asserted structurally in `test_schemas.py::test_synthesized_recommendation_has_no_identity_fields`). Those fields are re-bound in `nodes/synthesizer.py` by `AdvisorReport.from_synthesis`, from a **subject index** the node builds itself (`_build_subject_index`) out of `state["existing_fund_evaluations"]` (existing side) and the three specialists' candidates filtered in code to `action == "Buy"` (new-buy side, `_select_buy_candidates`) — never from anything the model says. A `pydantic-ai` `output_validator` (`_validate_synthesis`) checks every identifier the model names against that index *with the correct side enforced* (an existing-holdings identifier can never validate as a new-buy suggestion or vice versa) and against the run's real, live-derived platform set (`_derive_platforms`, from `state["holdings"]`'s real `platform` values — zerodha/moomoo/groww/sharekhan/real_estate, never hardcoded), raising `ModelRetry` (bounded by `retries=2`) on any violation, then propagating as `pydantic_ai.exceptions.UnexpectedModelBehavior` - a hallucinated or cross-contaminated identifier can never reach a recommendation.
- **The run-aggregate position-sizing cap lives in the same validator**, not the schema — `MAX_NEW_CAPITAL_PCT` is a property of the whole `new_buy_suggestions` list (sum of `position_size_pct_of_portfolio`), so it can't be expressed as a per-field `Field(...)` constraint the way the per-suggestion `MAX_NEW_POSITION_PCT` cap can. A set that passes every individual cap can still be rejected in aggregate (pinned by `test_synthesizer_node_raises_when_aggregate_capital_cap_exceeded`).
- **"Avoid is the default" is structural in four layers**, per the design spec: (1) code filters to `action == "Buy"` before the LLM call - non-Buy candidates only ever appear as a one-line "already considered and rejected" summary, never full reasoning (minimal-context cost rule 4, verified by `test_synthesizer_node_prompt_excludes_raw_holdings_and_non_buy_full_reasoning`); (2) the output_validator's membership check makes the Buy set a structural ceiling — the Synthesizer can only ever shrink it, never grow it; (3) `SynthesizedRecommendation`'s `model_validator` enforces `new_buy_suggestions == [] ⟺ no_new_buy_reason is not None` as a first-class, always-explained result; (4) when the Buy set is empty going in, the new-buy prompt block is omitted entirely (reject-early, no wasted LLM spend) and `no_new_buy_reason` is overwritten **deterministically in code** (`_deterministic_no_new_buy_reason`, real per-specialist evaluated/non-Buy counts plus what rejection memory suppressed) after the call returns, regardless of what the model wrote — a deterministic string can't drift. Pinned by `test_synthesizer_node_avoid_is_default_when_every_candidate_is_hold`.
- **Coverage is reported, not hidden.** `ReportCoverage` (built entirely in code, `_compute_coverage`) states plainly that only the 9 India mutual funds get an individual Conviction Gate verdict this phase — the 36 IN equities, 3 US equities, and 4 ETFs get allocation-level guidance only, since no Equity Holdings Analyzer exists yet (named as the natural Phase 9 candidate in both the design spec and here). No writes; the store guard (`store is None` → raise) is the same fail-loud pattern every store-using node in this graph already follows.
- **`get_synthesizer_model()`** (`models.py`) is its own, separately-named three-model `FallbackModel` chain (`nvidia/nemotron-3-super-120b-a12b:free` → `deepseek/deepseek-v4-flash-0731:free` → `z-ai/glm-5.3-flash` paid tail) — never inherited from the specialists' `get_specialist_model()` by convenience, per CLAUDE.md cost control rule 1. Free-first, since the Synthesizer reconciles already-tool-grounded specialist judgments rather than doing primary research (design spec's Model Choice section); accepted as proposed in the autonomous session's Decisions log, not yet exercised against a real paid call (see below).
- **The human-approval gate is a real `interrupt()`, in its own downstream node** (`human_approval_gate_node`), never inside the Synthesizer — live-verified this phase (design spec Background) that resuming an interrupted graph re-runs only the interrupted node, so putting the interrupt anywhere else would re-pay for the whole synthesis LLM call on every approval. Routing (`_route_after_synthesis` in `graph.py`, delegating to the gate module's own `_requires_human_approval` so the two can never drift apart) is a pure, deterministic predicate — `new_buy_suggestions` non-empty, or any `existing_holdings_guidance.action` in `{Sell, Reduce, AddTo}` (`AddTo` included per Decision 2: it commits fresh capital, same as the guardrail's original sell/buy wording is protecting against) — never the model's own opinion.
- **Fail-loud checkpointer guard.** `interrupt()` compiled without a real checkpointer was live-verified to return quietly with no error and no way to resume (the same class of silent-degradation hazard as Phase 7's `store=None` case) — `human_approval_gate_node` checks `config["configurable"]["__pregel_checkpointer"] is None` and raises before ever calling `interrupt()`, so an unresumable pause can't masquerade as a working gate.

> **REAL-MODEL GATE: RUN, AND IT FOUND A GENUINE PROBLEM — NOT YET RESOLVED.** The design spec's own flagged risk ("does `structured_outputs` genuinely work for the two free Synthesizer models through `pydantic-ai`'s OpenRouter path") was run for real, twice, in an isolated `git worktree` against a fresh `agent_memory.db` (never touching the shared one). It failed both times with `pydantic_ai.exceptions.UnexpectedModelBehavior: Exceeded maximum output retries (2)`, task `synthesizer`.
>
> **First run** — the raw model response was truncated mid-JSON (`Invalid JSON: EOF while parsing a list`). Root cause: `SynthesizedHoldingGuidance`/`SynthesizedNewBuy`'s `risk_flags`/`rationale`/`portfolio_assessment` fields had no length bound at all, so a real (thorough) model produced 6–9 long `risk_flags` per holding across all 9 real funds plus 2 new-buy candidates and ran out of output budget before finishing. **Fixed**, and this fix is real and worth keeping regardless of what's below: `schemas.py` now has `RISK_FLAGS_MAX_ITEMS`/`RISK_FLAG_MAX_CHARS`/`RATIONALE_MAX_CHARS`/`GAP_ADDRESSED_MAX_CHARS`/`PORTFOLIO_ASSESSMENT_MAX_CHARS`/`ALLOCATION_NOTE_MAX_CHARS`, enforced via `Annotated[str, Field(max_length=...)]` on every free-text field in the Synthesizer's output schema — a hard cap in code, not prompt wording, per CLAUDE.md cost-control rule 5. The system prompt also now states the same caps as an explicit, non-optional instruction (defense in depth, not instead of the hard cap). The Synthesizer's `Agent` also now sets `model_settings=ModelSettings(max_tokens=24000)` as a secondary safety net. 6 new tests in `test_schemas.py` pin all six new caps. Full suite re-run clean: 189 passed.
>
> **Second run, after the fix — failed differently, and this is the real unresolved finding.** No longer truncated (reached a JSON list literal), but the model itself produced genuinely malformed content under the "be concise" pressure: missing keys, garbled non-JSON fragments inside string values (e.g. `"HDFC HDFC HDFC [INF179K01WA6]"`, `"0.95 0.95 mid/small-cap (0.93 HDFC 0.90 50)"`), still failing `Invalid JSON: EOF while parsing a list`. This is not a token-budget problem — it's a real reliability gap in the free-tier model(s) actually honoring `pydantic-ai`'s structured-output contract for a schema this complex (9 existing-holdings entries + 2 new-buy entries, each nested).
>
> **Why this wasn't fixed further tonight, and why that's the right call, not a stall:** `pydantic_ai.models.fallback.FallbackModel` only falls to the next model in the chain on model-level errors (HTTP/connection failures, e.g. a 429) — it does **not** fall back when the *same* model exhausts its own `Agent(retries=2)` output-validation retries and raises `UnexpectedModelBehavior`. So in practice, this failure mode likely never reaches the paid `z-ai/glm-5.3-flash` tail at all — it fails out on the free model before FallbackModel would ever switch. Fixing this for real means one of: switching the Synthesizer's primary model away from a heavy reasoning model (`nvidia/nemotron-3-super-120b-a12b:free` likely spends much of its budget on internal reasoning before the final JSON, which may be *why* the final answer comes out compressed/garbled under a "be concise" instruction), reducing the schema's structural complexity further, or wrapping the `Agent.run()` call in a manual retry-with-different-model loop that `FallbackModel` doesn't provide out of the box. **All three are real per-node model-choice/architecture decisions — exactly the kind CLAUDE.md's cost-control rule 1 says must be Abhi's explicit call, never a silent default an agent keeps iterating on unattended.** Continuing to guess at model swaps overnight would have been exactly the "silent architectural choice" CLAUDE.md forbids, so this is disclosed instead of hidden or half-fixed.
>
> **What this means practically:** the graph's Synthesizer node is very likely to fail on a real run tonight, as built, until this is resolved — this phase is NOT yet cleared by the real-model gate.
