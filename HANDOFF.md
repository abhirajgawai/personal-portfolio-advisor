## How this project works (read before doing anything)

This project is built entirely through the **`superpowers`** Claude Code plugin's skill pipeline. Every phase follows the same sequence:

1. **`superpowers:brainstorming`** — classify the work as spike/bounded/architectural, ask clarifying questions one at a time, propose approaches, present a design section-by-section, get explicit approval. For architectural work, this ends with a written spec at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed to git.
2. **`superpowers:writing-plans`** — turns the approved spec into a granular, TDD-structured implementation plan at `docs/superpowers/plans/YYYY-MM-DD-<topic>.md` — bite-sized tasks, each with exact code, exact test assertions, no placeholders.
3. **`superpowers:subagent-driven-development`** — executes the plan: a fresh subagent per task, an independent task reviewer after each one (spec compliance + code quality), a ledger at `.superpowers/sdd/<plan-basename>/progress.md` tracking everything, a capped fix-loop when reviewers find real issues, and a final whole-branch review (on the most capable model) before merge.
4. **`superpowers:finishing-a-development-branch`** — merge/cleanup (the user has been doing actual merges themselves via GitHub PRs).

**Non-negotiable standing rules, all in `CLAUDE.md`:**
- **Explain-as-you-go**: before any implementation step, explain what/why/how; after, explain what changed and what it means. One piece at a time, confirmed before moving on. No silent scope growth.
- **Phased development**: each phase ends with real testing (pytest against real data, no mocks of `portfolio.db`) before the next phase is even planned. Once a phase's tests pass and it's merged, push `main` before starting the next phase's brainstorming.
- **Agentic workflow design principles** (11 of them): workflows before agents, small single-purpose units, explicit typed state (`TypedDict`s in `state.py`), separate gather/measure from judge/decide, fail loud never fabricate, tools as external MCP protocols not ad-hoc logic, guardrails as structure not instruction, reject-early gating, human-in-the-loop at consequential decisions, memory as a deliberate choice, observability is not optional.
- **LLM cost control** (7 rules): explicit per-node model choice (never silent default), reject-early before expensive calls, cacheable stable system prompts, minimal context per call, hard numeric caps enforced in code, bounded retries, long-term memory as a cost control.
- **Non-negotiable guardrails**: advisory only, never execution (no order-placement tool anywhere, ever); long-term investing only (no options/derivatives/day-trading); `portfolio.db` is read-only always (`mode=ro` URI, never edit `portfolio_data_mcp/server.py`); agent writes go only to `sandbox-data/agent_memory.db`; new-buy candidates must clear the full Conviction Gate or be explicitly rejected — "avoid is the default, not buy."

**Verification habit used throughout this session, worth continuing:** never trust a library's documented API shape — verify it live (`python -c "..."` against the actually-installed version) before writing plan code. This caught several real surprises (MCP tool result shapes, `yfinance-mcp`'s `symbol` not `ticker` argument, a webpage-only model alias that wasn't a valid API ID, `FilteredToolset` not exposing `direct_call_tool`). Reviewers in this session also independently re-verified claims rather than trusting reports — re-running tests themselves, reading library source to confirm a monkeypatch pattern, hand-tracing cap logic against concrete scenarios. Keep that standard.

## What's actually done (merged to `main`, tested, working)

**Phase 1 — Research node.** `src/agentic_frameworks/graph/nodes/research.py`. Fetches real holdings via the existing `portfolio_data_mcp` server (a separate project at `E:\agentic-portfolio-dashboard`, its own venv, launched as a stdio subprocess). Groups holdings by asset_class × geography. Real portfolio: ₹10.29M, mixed IN/US, mixed equity/fund/real-estate.

**Phase 2 — Risk Analyst node.** `src/agentic_frameworks/graph/nodes/risk_analyst.py`. Pure functions (no LLM, no MCP) computing four risk views from Research's output: concentration, category overlap (sector-based diversification proxy), currency exposure, liquidity (real-estate vs everything else). Reports raw numbers only, no verdicts — judgment is deferred to later nodes.

**Phase 3 — Graph Harness.** `src/agentic_frameworks/graph/graph.py`, `checkpointer.py`. First time the system ran as an actual `StateGraph`, not isolated functions. Linear `Research → Risk Analyst`, backed by a real `AsyncSqliteSaver` checkpointer writing to `sandbox-data/agent_memory.db` (gitignored, created fresh). Proved memory persistence works via a real end-to-end run.

**Phase 4 — US Equity/ETF Specialist.** `src/agentic_frameworks/graph/nodes/us_equity_etf_specialist.py`. First LLM-calling node, first `pydantic-ai` usage, first real spend of money on a paid API. Three-stage pipeline: (1) an LLM candidate generator proposes tickers per gap sector, capped in code at 3/sector and 5/run (never trusting the model's own count); (2) each candidate is verified against real `yfinance-mcp` data before any expensive evaluation runs (reject-early — this is also the safeguard against LLM-hallucinated tickers, since a fake ticker returns a near-empty payload rather than raising, and `longName` presence is the confirmed reliable signal); (3) surviving candidates go through a Conviction Gate evaluator (portfolio-fit → fundamentals → valuation → style-fit, reject-early on first failure), producing a strictly validated `CandidateEvaluation` per candidate.

- **Model:** `deepseek/deepseek-v4.1-flash` primary via OpenRouter, `z-ai/glm-5.3-flash` backup (added mid-phase after DeepSeek's shared free pool returned genuine repeated 429s — confirmed via `pydantic_ai.models.fallback.FallbackModel`, which triggers on `ModelAPIError`, live-confirmed a 429 raises as a subclass of that).
- **Data source:** `yfinance-mcp` (external package, launched via `uvx yfmcp@latest`, not a project dependency — same "sibling subprocess" pattern as `portfolio_data_mcp`). Covers US equity, US ETF fundamentals/holdings, AND India equity (via `.NS` ticker suffix, live-verified against real NSE stocks). Options/derivatives/intraday-gapper tools are structurally excluded from the toolset via `.filtered()` — not just told not to use them, actually can't reach them.
- **Required real-model gate:** every LLM-calling phase must include one real, deliberate, cost-bounded run against the actual paid model, reviewed by the user, before the phase counts as done — this is what caught a genuine bug (`confidence` field had no bounds, model returned `7.0` once) that no amount of `TestModel`-only testing could have found. `TestModel` (free, `pydantic_ai.models.test`) is used for all automated tests of LLM-calling logic; the real check is separate and manual.
- **Post-merge fix (2026-09-11, bounded, no branch):** the portfolio-fit check was a tautology (told a sector is a gap, asked to confirm it, no real data). Fixed: the node now builds a real holdings summary from `state["holdings_by_bucket"]` at call time (not hardcoded), baked into the Conviction Gate's system prompt. Verified end-to-end against the real graph output — genuinely reflects your actual 6 US holdings (GOOGL, IBM, MU, SMH, VOO, IAU), and updates automatically as the portfolio changes.

**Phase 5 — India Equity Specialist.** `src/agentic_frameworks/graph/nodes/india_equity_specialist.py`. Second new-buy specialist, same three-stage pipeline as Phase 4 (propose → verify → Conviction Gate), reusing the same model pair and `yfinance-mcp` toolset (already confirmed to resolve `.NS`-suffixed NSE tickers). One real design change from Phase 4: gap sectors are **computed live from real holdings** (`_compute_india_equity_gaps`, `_compute_us_gaps`), not a hardcoded list — this also retrofitted a real bug fix into the Phase 4 US specialist, whose hardcoded `US_GAP_SECTORS` list was found to omit "Information Technology" (frozen at a point in time when the portfolio already held it). `ProposedCandidate.sector` was generalized to validate against the full 11-bucket GICS taxonomy (`GICS_SECTORS`), shared by both specialists. Both specialists are now wired into `build_graph()` as parallel branches off `risk_analyst` — the graph's first real fan-out (both still dead-end at `END`, no Synthesizer yet). `_apply_candidate_cap` was extracted into a shared `nodes/_specialist_helpers.py` module to avoid duplicating cap logic between specialists.

- **Design decisions, confirmed with the user during this phase's brainstorming:**
  - Gap computation is equity-only for both specialists — ETF `sector` values (e.g. "US Large Cap", "Gold") aren't real GICS sectors, and mutual fund `sector` values are fund *category* not GICS sector; including either would mean fabricating coverage that isn't actually known. Whole-portfolio gap analysis (rolling up sector coverage across mutual funds too) was explicitly deferred to the future Mutual Fund Specialist phase, which can supply real fund-holdings sector data.
  - **Real estate is the one exception:** since the user's real estate holding is a directly known fact (not an inferred category), `_compute_india_equity_gaps` treats "Real Estate" as covered whenever `holdings_by_bucket["real_estate"]["IN"]` is non-empty — confirmed against the real portfolio to correctly leave `{"Energy"}` as the only current India equity gap (previously `{"Energy", "Real Estate"}` before this fix).
- **Post-final-review fixes (same phase, before merge):**
  - The whole-branch review caught that widening `ProposedCandidate.sector` to the full GICS taxonomy (needed for live gap computation) removed the schema-level guarantee that a candidate actually addresses a gap. Fixed: a shared `_filter_to_gap_sectors` helper drops off-gap candidates before the cap/verification/evaluation stages, in both specialists. Also added reject-early: both nodes now return an empty candidate list immediately if the live gap list is empty, before any model/toolset setup — avoiding a real LLM call on an empty-content prompt.
  - **Real-model verification (2026-09-11) caught a second, more serious bug:** `get_yfinance_toolset()` had `tool_error_behavior="error"`, meaning ANY tool-call problem (including a benign one, like the model omitting a required argument) crashed the whole node with a hard `fastmcp.exceptions.ToolError`, rather than giving the model a bounded chance to self-correct via `ModelRetry` (already bounded by the existing `Agent(retries=2)`). This crashed the very first real-model run, live, on a real `yfinance_get_price_history` call missing its `symbol` argument. Fixed by switching to the library default `tool_error_behavior="retry"`. Re-verified: a subsequent real run hit two more real, legitimate tool errors (yfinance 404s for ONGC.NS and XLF fundamentals data) and recovered gracefully instead of crashing, producing 5 real US candidates (Health Care: XLV/UNH/JNJ Hold/Buy/Hold; Financials: XLF/JPM Buy/Hold) and 3 real India candidates (all Energy: RELIANCE.NS/ONGC.NS/IOC.NS, all Buy) — reviewed by the user, all confidence values valid (0.6–0.72), all genuinely advisory, no fabricated data.

**Phase 6 — Mutual Fund Specialist.** Two new, single-purpose nodes covering the real 9 IN mutual fund holdings: `mutual_fund_holdings_analyzer_node` (`src/agentic_frameworks/graph/nodes/mutual_fund_holdings_analyzer.py`, judges existing holdings — first node in this project to do real LLM-driven judgment of *existing* holdings, not just new-buy candidates) and `mutual_fund_specialist_node` (`.../mutual_fund_specialist.py`, proposes/evaluates new-buy candidates, mirroring the equity specialists' propose→verify→evaluate pipeline). Both wired into `build_graph()` as two more parallel branches off `risk_analyst` — the graph now has 4 parallel branches, all still dead-ending at `END`.

- **First custom, self-written MCP server this project has built:** `src/agentic_frameworks/mfapi_mcp/server.py`, wrapping `MFapi.in` (free, no-auth Indian mutual fund NAV/scheme API) with `search_scheme`, `get_scheme_nav`, and `get_scheme_meta` (a lightweight `/latest`-endpoint tool added during final review to avoid downloading full NAV history just to check a scheme's ISIN/category). Built with the official MCP SDK's `mcp.server.fastmcp.FastMCP` (already installed transitively via `pydantic-ai`, no new dependency). Chosen over several pre-built MFapi-wrapping MCP servers found on the market, after determining none of them covered this project's actual requirements (ISIN-matched resolution against exact holdings, category-gap detection against a curated taxonomy, cross-fund redundancy across the specific 9 real funds) — those are business logic no generic tool would have. This also picks up the "build an MCP server yourself" learning goal explicitly deferred from Phase 4's `yfinance-mcp` reuse decision.
- **A substantial new pure-computation layer** (`src/agentic_frameworks/graph/nodes/_mutual_fund_helpers.py`), mirroring the Risk Analyst's measure-not-judge pattern: ISIN-matched scheme-code resolution (deterministic, with progressive-query-shortening and letter-digit-normalization fallbacks, live-verified against all 9 real holdings including one genuine naming-mismatch edge case — "Nifty200" vs `MFapi.in`'s "Nifty 200"), NAV-history fetching/parsing, CAGR/volatility/max-drawdown metrics (stdlib `statistics` only, no numpy/pandas — confirmed not even installed in this project's venv), benchmark-difference computation via the already-integrated `yfinance-mcp` (a curated `MF_CATEGORY_BENCHMARK_TICKERS`/`INDEX_FUND_BENCHMARK_TICKERS_BY_ISIN`, live-verified: exact-index matches for 2 of 4 existing index funds, category-proxy matches for equity categories, confirmed unavailable for hybrid/debt categories), and cross-fund NAV-return correlation (a statistical proxy for portfolio-holdings overlap, which no free data source exposes directly).
- **A redefined 7-check Conviction Gate for funds** (portfolio-fit/redundancy → cost (qualitative Direct-vs-Regular only, since `MFapi.in`/AMFI's own feed confirmed to have no expense-ratio field at all) → performance-vs-benchmark → risk-adjusted performance (volatility + max drawdown, not Sharpe — no clean Indian risk-free-rate source found) → cross-fund redundancy → track-record length → style-fit), with static India MF tax-treatment domain knowledge (equity vs. debt fund capital-gains rules, ELSS's 3-year lock-in) baked into both nodes' system prompts.
- `MF_CATEGORY_TAXONOMY` (13 curated categories) was deliberately placed in `schemas.py` alongside `GICS_SECTORS`, matching this project's established layering (node modules import taxonomy constants from `schemas.py`, never the reverse) — caught and fixed during this phase's own pre-flight review before any code was written.
- `_apply_candidate_cap`/`_filter_to_gap_sectors` (shared by all three new-buy specialists) were generalized to accept a `key=` parameter (default `lambda c: c.sector`, unchanged for the two equity specialists; `lambda c: c.category` for mutual funds) — zero behavior change to existing callers.
- **Explicitly out of scope, disclosed:** category peer-ranking (comparing a fund against all peers in its category, not just one benchmark index — a real, larger cost/scope expansion, deferred); true Sharpe/Sortino ratios; client risk-profile/goals-based asset-allocation suitability (no such data exists anywhere in this system); AMC/fund-manager governance/news monitoring (a web-search-shaped capability, same tradeoff already rejected in this project); numeric expense ratio and AUM (confirmed unavailable from every free source checked); underlying portfolio-holdings concentration within a fund.
- **Post-final-review fixes (same phase, before merge):** the whole-branch review found a real correctness bug — `mutual_fund_specialist_node` verified a new-buy candidate's name resolved to *some* real Direct-plan fund, but discarded the resolved identity/category and kept using the LLM's originally-proposed name/category for metrics, benchmark lookup, and the evaluator prompt, meaning real financial data could be silently attached to a different fund than the one shown to the user. Fixed: the candidate is now rejected if the resolved category doesn't correspond to the claimed category, and the verified scheme's real name is used downstream. Also fixed in the same pass: the new-buy Conviction Gate's portfolio-fit check had no real holdings/gap context (unlike the equity specialists' `holdings_summary` pattern) — added; cross-fund redundancy was rendered to the LLM as bare ISINs with no fund names — added an ISIN→name map; and `max_drawdown` was returning a fabricated `0.0` (not `None`) on single-entry history, same fabrication class as an earlier fix to `cagr_since_inception`/`volatility` — corrected. **Real-model verification (2026-09-13):** produced 9 real existing-fund evaluations and 1 real new-buy candidate (a Multi Cap fund, correctly targeting a live-computed gap), all confidence values valid (0.56–0.8), benchmark-unavailable cases explicitly stated (not guessed), and the two Small Cap holdings correctly showing 0.95 mutual correlation — confirming the whole redundancy pipeline works end-to-end against real data.
- **Known, disclosed gap (not fixed this phase):** `CandidateEvaluation` (shared by all 4 specialist/analyzer nodes) has no field identifying *which* fund/candidate a verdict belongs to — only implicit via list order and free-text `reasoning`. Pre-existing since Phase 4, not introduced this phase, but flagged as worth a small fix before the Synthesizer phase locks the shape in. **Not yet decided with the user which way to go.**
- **Known, disclosed cosmetic issue:** 5 commits in this phase have the wrong model name in their `Co-Authored-By` git trailer (from `haiku`-dispatched subagents defaulting to their own self-identification instead of the session-mandated attribution), and 2 have no trailer at all. Not corrected via history rewrite (would invalidate the SDD ledger's commit-hash trail across ~10 already-reviewed tasks for a purely cosmetic issue). Fixable later via rebase if desired.
