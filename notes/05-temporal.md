# Learning Checkpoint — Temporal

Built the night of 2026-09-19: a Workflow + one coarse Activity wrapping `build_compiled_graph()`, an OS-level advisory lock on `agent_memory.db`, and a deliberately-not-activated recurring Schedule. See `docs/superpowers/specs/2026-09-19-temporal-design.md` and the Phase 10 section of `HANDOFF.md` for the full build record.

## 1. What problem does this solve that a plain LLM API call / plain cron job doesn't?

A cron job that dies mid-run either re-runs everything from scratch or silently does nothing until someone notices. Temporal's workflow-history replay means a crashed Activity is retried without the Workflow forgetting what already happened — and because this project derives the graph's `thread_id` deterministically from the schedule date rather than a random UUID, a retried Activity resumes the *LangGraph checkpointer's* progress too, so a crash doesn't duplicate paid LLM work already done earlier in the same day's run. Two separate durability layers, doing two genuinely different jobs, not one duplicating the other.

## 2. What did it make easy that was hard/verbose without it?

- **Schedule-level dedup** (`ScheduleOverlapPolicy.SKIP`) is a one-setting way to stop the Temporal server from starting a second scheduled run while one is still in flight — cheap to configure, though (see below) not sufficient on its own.

## 3. What did it make hard or awkward?

- **The obvious answer was the wrong one, and only checking the shipped plugin's own source caught it.** `temporalio` 1.33.0 ships an official (experimental) `LangGraphPlugin` that runs each LangGraph node as a Temporal Activity automatically. Its own README says stores aren't supported — which would crash three of this project's nodes outright, since Phase 7 made "no store" a fail-loud error rather than a silent degradation — and its suggested resume path is a Temporal *signal*, which is exactly the machine-reachable auto-approve path Phase 8's no-self-approval guarantee exists to forbid. The design instead wraps the whole compiled graph in one Activity and keeps the Workflow to pure orchestration. Worth remembering generally: an official integration being "the obvious choice" doesn't mean it fits a system with guardrails the integration wasn't designed around — check its actual constraints against your own before adopting it.
- **Temporal's own concurrency control is blind to anything that doesn't go through the Temporal server.** `ScheduleOverlapPolicy`/`WorkflowIDReusePolicy` only prevent two *Temporal workflow instances* from overlapping — a manual `python -m ...` script opening `agent_memory.db` directly never touches the Temporal server, so server-side dedup can't see it. The only layer both a scheduled run and a manual run share is the operating system, which is why the real fix is an OS advisory lock placed *inside* `get_checkpointer()`/`get_memory_store()` themselves (the only two functions anything in this codebase uses to open that database), not at some Temporal-specific entry point. A framework's own safety mechanism can have a scope boundary that isn't obvious until you ask "what happens if this thing didn't go through the framework at all."
- **Local test infrastructure that starts a real subprocess can hang, silently, for hours.** `temporalio.testing.WorkflowEnvironment.start_local()` downloads and runs a real dev-server binary for its time-skipping test server — and it hung on this exact Windows machine during this session's own test run, requiring a manual process kill hours later. This is the second independent local-dev-server hang found on this Windows build in one night (LangGraph Studio's own local server has an open upstream issue for the same failure mode) — worth treating "start a real local server as part of an automated test" as a genuine reliability risk on this OS, not a one-off fluke.
- **Determinism constraints are easy to violate by habit.** `datetime.now()` inside Workflow code is a real determinism bug (Temporal replays workflow code, and a wall-clock read that gives a different answer on replay breaks that); `workflow.now()` is required instead, and it's the kind of mistake that wouldn't show up until a workflow actually gets replayed.

## 4. When would you reach for this in a real job?

Any unattended, scheduled, or long-running process where "durable" needs to mean something more than "restart it and hope" — daily/hourly jobs that call paid APIs (where re-running from scratch after a crash is a real cost, not just an inconvenience), anything with a human-approval step that might not get answered for days, or a pipeline where partial progress genuinely matters. Not worth the operational overhead (a running Temporal server, workflow/activity boundaries, determinism discipline) for a simple, cheap, idempotent script where "just run it again" is an acceptable failure mode.
